# 标准工作流（WORKFLOW）

> 面向 agent 与人类协作：新需求怎么登记、反问、确认、实施、提交、完成定义。编码纪律见 `AGENTS.md`，技术实现细节见 `DESIGN.md`。

## 一、需求输入与反问（人类 + AI）
人类说出自然语言需求后，AI：
0. **开工前文档闸门（强制）**：先检查 `requirements/R-xxx-<slug>.md` 是否存在，没有就先创建需求文档；再检查 `development-design/R-xxx-<slug>.md` 是否存在，没有就先创建开发设计。**两份文档缺一份不得改业务代码**（线上明显 bug 可先定位修复，再补登记与设计）。`scripts/check_doc_consistency.py` 会对 R-237 起的需求校验两者成对存在。
1. **原样登记**：先记 `requirements/R-xxx.md`（原文，禁止改写删减；编号取 `requirements/` 现存最大 +1，与 README 索引同步）
2. **反问清单（10 项，逐项过，不许跳过）**：
   1. 范围与边界——包含什么？明确不包含什么？
   2. 场景与影响——在哪用？影响现有功能吗？
   3. 数据——需要哪些新数据？来源可靠吗？拿不到怎么办？
   4. 边界与异常——空数据、失败、重复、极端情况？
   5. 验收标准——怎么算完成？可测试吗？
   6. 成本与性能——多花钱吗？拖慢系统吗？
   7. 依赖与风险——依赖外部服务吗？它挂了怎么办？
   8. 优先级——现在做还是排期？
   9. 动效（R-175 起必问）——列表/卡片入场、TAB 切换、抽屉/弹窗、加载与状态变化，该有的动画不能省，且美观流畅。
   10. 非实时返回（R-202 起必问）——同步还是耗时/后台返回？**所有非实时结果必须有进行中动效，且切页/刷新回来仍能恢复「进行中」**（否则误以为已完成）。
3. **复述确认**：把「需求 + 反问答案 + 你的理解」复述给作者；作者确认后才写业务代码。
   （线上**明显 bug** 可先定位根因、直接修复并登记，不必等待「继续」，但要说明根因与影响。）
4. **写入归档**：原文 + 反问 + 确认/处理结论全部进 `requirements/R-xxx.md`。产品需求文档固定按以下五部分写详细，确保没有技术背景的读者也能看懂：
   1. **需求背景**：谁在什么场景遇到什么问题，为什么现在需要解决。
   2. **想要实现的目标**：完成后用户能得到什么结果，包含什么、不包含什么。
   3. **页面数据来源**：每类数据从哪里来、何时更新、需要什么权限、拿不到时页面怎样显示。
   4. **功能需求**：需要哪些页面；每个功能、按钮分别干什么；页面包含哪些字段；逐字段写清中文含义、来源和空值表现；同时写清操作结果、异常、加载与动效。不能只写模块名称或技术实现。
   5. **用户故事**：用「作为……，我希望……，以便……」描述主要使用过程，并写清完成后的可见结果。

## 二、PRD 与里程碑更新（AI）
- 更新 `docs/PRD.md`（范围/现状/验收）
- 在 `docs/milestones.md` 新增/调整条目（里程碑 = M 序号；需求 = R-xxx，两者对应）
- 展示计划，等作者说「继续」才写业务代码（bug 修复除外）

## 三、开发设计（AI，编码前）
- **编码前先过文档闸门**：确认需求文档 `requirements/R-xxx-*.md` 与开发设计 `development-design/R-xxx-*.md` 都已存在；缺哪个先补哪个，缺文档不得动手改代码（见 `AGENTS.md` 新需求流程第 0 步）。
- **每个需求都必须先写开发设计**，统一放在与 `requirements` 同级的 `development-design/` 目录，文件名为 `development-design/R-xxx-<short-description>.md`；写设计不等于开始编码。
- 固定包含八部分：
  1. **开发背景**：对应需求、现状、要解决的问题和边界。
  2. **涉及的技术**：现有技术、复用模块、新增模块和依赖；不能假设项目已有未确认的库。
  3. **开发流程图**：从用户操作到后台处理、结果展示和异常恢复。
  4. **数据流转图**：外部数据、数据库、规则计算、AI、接口和页面之间的流向。
  5. **实现细节**：复杂功能必须写清输入、计算步骤、规则、阈值、证据、排序、去重、空数据与失败降级。例如“为什么差”“凭什么算同行/爆款”“下一个主题凭什么推荐”，不能只写“AI 分析”。
  6. **新增或修改的表结构**：逐表逐字段写类型、是否可空、默认值、中文含义、索引和唯一约束。
  7. **新增或修改的接口**：逐接口写方法、路径、用途、请求参数、响应字段、状态码、错误和幂等规则。
  8. **数据来源与原始字段明细**：逐项说明原始数据来自第三方接口、现有功能/数据库表、作者输入还是程序计算；写清原始字段名/路径、中文含义、清洗或计算公式、落库字段、使用页面、更新时间、权限和空值处理。原始响应 key 未公开时不得猜测，须标注需用真实样例确认。
- 设计中的表和接口在实施前都是拟定方案；实施后必须同步真实的 `docs/DATABASE.md`、`docs/API.md`。

## 四、实施与自愈（AI）
- 按里程碑实现，顺序遵守依赖
- 每完成一个里程碑：`scripts/verify.sh`（lint + 类型检查 + 测试 + 构建）→ 修复全部失败 → 再验证
- 涉及外部依赖（DeepSeek/阿里云/TikHub）的测试一律 mock，保证离线可跑；**线上联调走真实模式**
- 涉及接口/表结构：用自动生成器刷新 `docs/API.md`、`docs/DATABASE.md`
- UI 类功能输出截图/预览供作者确认
- **AI 自测（强制，交付前必做）**：
  1) scripts/verify.sh 全绿；
  2) 相关后端接口冒烟（真实或 mock，跑通关键链路）；
  3) 前端关键交互点检（无 JS 报错，弹窗/按钮/勾选/跳转可用）；
  自测不过 = 不算完成，不许说“做好了”。
- **保持服务运行（强制）**：改动完成后确认后端 http://127.0.0.1:8000 与前端 http://localhost:3000 都在运行并已加载最新代码（必要时重启），health/页面可访问后再交付。

## 五、记录与提交（AI）
- 更新需求状态（已登记→澄清→已确认→实施中→已完成/搁置/拒绝）
- 更新 `docs/milestones.md` 勾选进度；追加 `docs/CHANGELOG.md`
- commit 信息带需求编号：`feat(R-xxx)` / `fix(R-xxx)` / `docs(R-xxx)`
- 每个需求一个 commit，不夹带无关改动

## 六、定义完成（Definition of Done）
- [ ] 需求文档 + 开发设计文档成对存在且与实现一致（缺文档不得开工/交付）
- [ ] 代码通过 `scripts/verify.sh`
- [ ] AI 已自测：verify + 相关接口冒烟 + 前端关键交互，均通过
- [ ] 动效点检：新交互都有动效且流畅，切换类无空白闪帧（首帧 opacity ≥0.6、落定 1/none）——规范见 `DESIGN.md` §8
- [ ] 非实时结果可见（R-202）：耗时/后台返回的功能有进行中动效，且切页/刷新回来仍能恢复「进行中」——规范见 `DESIGN.md` §8.6
- [ ] 服务运行中：后端/前端已启动并加载最新代码，health 与页面可访问
- [ ] 验收标准逐条可验证
- [ ] 需求状态已更新，PRD/里程碑/CHANGELOG 已同步
- [ ] 已提交，commit 带编号
