# 关键设计决策（DECISIONS）

> 记录重要技术决策与原因，防止后续 agent 重复质疑或改坏。
> 新增决策请追加，编号 D-xxx。

---

## D-001：单用户轻量单体架构
- **决策**：单进程 FastAPI 单体应用，不引入 Redis / 消息队列 / 微服务
- **原因**：单用户规模，NAS 资源有限（N150/4C12G），越简单越可靠
- **扩展路径**：模块化 + 适配器模式，未来加 Redis 队列或拆分服务时业务逻辑不动

## D-002：SQLite + Alembic，不用 Postgres
- **决策**：数据库用 SQLite，迁移用 Alembic
- **原因**：单用户写入量小，SQLite 零运维、备份即拷文件
- **代价**：并发写受限（单用户无感）；若未来多用户再迁 Postgres

## D-003：LLM 使用 DeepSeek
- **决策**：所有 LLM 调用（人设分析/匹配打分/生成/复盘）走 DeepSeek API
- **原因**：中文语气质量好、成本低；批量调用（每日热点匹配）成本可控
- **扩展路径**：LLM 走适配器，可随时换 Qwen/GPT/Claude

## D-004：ASR 使用阿里云
- **决策**：视频转写用阿里云 ASR API
- **原因**：NAS 本地跑 Whisper 太慢（纯 CPU），云 API 一次性处理 50 条成本低
- **替代**：faster-whisper 本地仅作应急

## D-005：长任务用 DB 任务表 + 后台线程，不用队列
- **决策**：批量转写、生成等长任务的状态写数据库，由后台线程执行
- **原因**：单用户下 Redis/RQ 是过度设计；DB 任务表还能提供历史记录

## D-006：前端 Vue 3 + Vite SPA
- **决策**：前端用 Vue 3 + Vite 构建 SPA，由后端托管静态产物
- **原因**：脚本编辑工作台交互多，SPA 体验好；Vue 生态成熟

## D-007：需求归档双写（文件为事实源）
- **决策**：需求归档以 `requirements/` 文件为事实源，数据库同步索引供 Web 展示
- **原因**：任何 AI 工具都能读文件；git 提供不可变留痕；DB 提供检索/展示

## D-008：开发与运行分离
- **决策**：代码在笔记本开发，NAS 只跑 Docker Compose 产物
- **原因**：开发体验好、可测试；NAS 保持纯净只运行

## D-009：WorkBuddy / 微信通道暂不接入
- **决策**：不进入当前里程碑，列为未来扩展
- **原因**：避免系统被 WorkBuddy 桌面端在线状态绑架；先跑通 Web + 邮件核心闭环
- **扩展路径**：推送用 ClawBot iLink 通道；对话用 FastMCP 把 FastAPI 业务包装成 MCP 连接器

## D-010：项目命名为 echo（回声）
- **决策**：项目名 `echo`，中文名"回声"
- **原因**：寓意"复现作者的声音/语气"，贴合人设+语气核心
- **命名细节**：仓库目录 `echo/`；Python 包 `echo`；SQLite 文件 `echo.db`；Docker 服务/镜像 `echo`；前端包名 `echo-web`；环境变量前缀 `ECHO_`（如 `ECHO_DEEPSEEK_API_KEY`）
- **注意**：`echo` 为通用词，代码内一律用项目命名空间（包名/前缀），避免歧义

## D-011：五维工程标准（简单/易读/可靠/扩展/性能）
- **决策**：代码必须满足 简单、易读、可靠、扩展性高、性能好 五个维度，并通过 `scripts/verify.sh` 质量门禁（lint + 类型检查 + 测试 + 构建）
- **原因**：项目长期由 AI 维护，代码可读性和可验证性是可持续性的前提
- **执行**：M0 起写入 AGENTS.md 硬性规则；新增依赖需说明理由；分层依赖方向 api→services→models；适配器模式负责扩展

## D-012：需求反问机制（强制）
- **决策**：任何新需求，agent 必须先用"需求反问清单"（范围/场景/数据/异常/验收/成本/依赖/优先级 8 项）追问作者未考虑的问题，作者确认后才进入 PRD 与排期
- **原因**：需求原文 + 反问 + 确认结论全留档，才能保证"留档"有质量，避免 agent 拿到含糊需求直接开做
- **执行**：M0 起写入 AGENTS.md 硬性规则与 docs/WORKFLOW.md；反问内容随需求文件（requirements/R-xxx.md）一起归档

## D-013：视频导入双通道
- **决策**：Web 上传 + NAS `data/inbox/` 文件夹自动监听（拖入即转写入库）
- **原因**：发布端在手机，降低"把视频弄进系统"的摩擦

## D-014：风格样本检索用本地 BM25/TF-IDF
- **决策**：语气一致性检索用本地 BM25/TF-IDF，不引入云端 embedding
- **原因**：单用户 + 样本量小，本地零成本够用；少一个外部依赖

## D-015：AI 对话页权限边界
- **决策**：只读问答直接答；写操作（生成/改稿/删除）必须先经作者确认
- **原因**：防止对话页误触发动作

## D-016：主赛道字段
- **决策**：每条视频一个主赛道 + 可选副标签；赛道雷达按主赛道聚合
- **原因**：避免一视频多标签导致统计口径混乱

## D-017：可靠性细节（必做）
- 每日流水线幂等（同日不重复生成/推送，可续跑）；Web 手动触发按钮；转写后 AI 校对；热点快照 30 天/指标全留/视频可归档

## D-018：移动端响应式适配
- **决策**：Web 做移动端响应式适配，手机浏览器可用（阅读、确认、快速改稿）
- **备注**：最初决定不做，后作者确认需要（手机看邮件/快速查系统的场景真实存在），改为做
- **执行**：Vue SPA 采用响应式布局，进入 M2 验收

## D-017：视频平台/赛道改为多选（覆盖 D-016 的主赛道单选）
- **决策**：`videos.platform`/`main_topic` 单值字段升级为多选 `platforms`/`main_topics`（JSON 数组），存量单值迁移为数组
- **原因**：作者实际一稿多发（多平台）、内容常跨赛道；单选导致录入失真
- **口径**：看板/复盘/雷达按视频选中项各自聚合，一条视频可同时计入多个赛道/平台；统计为"该赛道/平台下视频集合的表现"，不做权重拆分（单用户口径足够简单）
- **注意**：改稿差异/人设学习不依赖平台赛道，不受影响；AI 预打标签输出改为可多值

## D-018：封面由作者上传，不自动抽帧
- **决策**：素材库封面 = 作者上传 jpg/png（存 `data/covers/`，视频表加 `cover_path`），不做 ffmpeg 自动抽帧
- **原因**：NAS 纯 CPU 抽帧重、作者本就要人工选封面；上传最轻
- **扩展路径**：未来需要"建议截取秒数/自动抽帧"再加 ffmpeg 适配器

## D-019：前端体验升级技术取向（R-015~R-018）
- **决策**：
  1. 视觉：参考 seanhalpin.xyz 极简文艺；引入轻量 UI 组件体系（可用外部 UI 库，实施时选定并说明理由）；系统字体栈 + 内联 SVG，不依赖外部 CDN
  2. 草稿/文案正文采用 **Markdown 为存储与编辑格式**（所见即所得式 Markdown 编辑器 + 渲染），不用 HTML 富文本
  - **原因**：草稿正文是文本管线（AI 生成/改稿差异/人设学习全部按纯文本 diff），Markdown 既提供"类富文本"观感（标题/加粗/列表/引用），又不破坏 diff 与生成链路；HTML 富文本需额外迁移 + 抽纯文本做 diff，成本高
  3. 编辑器支持插图：图片上传存 `data/uploads/`，以相对 URL（`/uploads/xxx.png`）写入 Markdown，前端挂载静态目录可显示
  - **原因**：作者要在平台直接写文案，口播脚本/正文常配参考图；图片即本地文件，零外部依赖
  4. AI 对话：多会话模型 + SSE 流式输出 + Markdown 渲染
  - **原因**：ChatGPT 式体验需要会话隔离历史；流式提升等待体验；Markdown 与草稿渲染共用一套解析


## D-020：通知中心采用任务表轮询 + 通知入库
- **决策**：后台任务结束（done/failed）自动写入 `notifications` 表；前端右上角铃铛轮询（5s）拉取，红点+下拉列表，点击标记已读并 `location.hash` 跳转目标页
- **原因**：单用户内网，无推送基建；复用既有 `background_tasks` 任务线程，在收尾处落通知最简
- **扩展路径**：未来若需跨设备推送可加 WebSocket/SSE 或邮件通知适配器


## D-021：全量风格学习采用"统计画像 + 加权样本注入"（R-020）
- **决策**：生成时（1）把所有非广告素材实时统计成"风格画像"（口头禅/句长/反问/感叹占比/标志性语气词）注入 prompt；（2）风格样本按"表现加权 × 时间衰减"排序并去重后取 top-k 注入；（3）草稿支持 1-5 分打分，进入反馈/选题学习
- **原因**：50+ 条素材后，仅靠 top3 原文无法稳定"无 AI 感"；统计画像让模型按数据模仿，加权让"数据好的、近期的"风格被优先模仿；全量实时统计天然覆盖作者后来上传的所有素材
- **注意**：素材越多画像越稳；广告（is_ad）全程隔离；打分 1-5 由作者在草稿卡上完成


## D-022：AI 提示词版本化存库（R-021）
- **决策**：各功能系统提示词默认值仍留在代码常量（首次启动 seed 入 `ai_prompts` 表 v1），运行时从 DB 读取当前 enabled 版本；编辑/优化=另存新版本（enabled 或 candidate），历史版本可随时启用
- **原因**：作者要"上传新素材后提示词自动演进且可回滚"；DB 版本化天然支持候选/启用/归档，代码常量作兜底默认
- **注意**：候选版不自动启用，避免质量波动；自动优化失败保留当前版并通知


## D-023：AI 是学习引擎，提示词只是方向盘（R-022）
- **决策**：定位上"让 AI 更像作者"主要靠数据闭环（风格画像/加权样本/打分/改稿差异），提示词版本管理只承担"可控迭代"；自动优化永不直接启用（候选制 + 每 3 条素材节流 + 启用前 diff + 金样本自测提示）
- **原因**：防止提示词管理喧宾夺主——每次上传就改提示词会过拟合单条、提示词膨胀、丢掉硬约束，最终让输出"变傻"而非"更懂"
- **执行**：R-020 数据闭环为发动机；R-021/R-022 为仪表盘与护栏；未来可评估作者数据微调（LoRA）作为更深的"学习引擎"


## D-024：双模型讨论生成（R-023）
- **决策**：LLM 统一 OpenAI 兼容适配（DeepSeek/Kimi 可插拔，模型名 env 可配）；素材学习/人设/画像/打分两模型完全共用；生成策略可切（固定/随机/轮流，页面设置）；每篇强制"初稿 + 5 轮互评修订"，讨论逐轮写 draft_discussions 留痕
- **原因**：双模型交叉评审可压"自说自话"与 AI 感，且留痕可审计每次定稿依据；成本高但作者明确要求
- **降级**：任一方不可用自动退回单模型；Kimi 未配置时以 DeepSeek 完成并留痕

## D-025：默认生成组合 = Kimi 生成/修订 + DeepSeek 评审（R-023 实测定稿）
- **决策**：作者对同话题 A/B 双模型对比稿实测打分，#19（Kimi k2.6 起草/修订 + DeepSeek deepseek-chat 评审）优于 #17（DeepSeek 起草 + Kimi 评审）
- **配置**：generation_model=kimi（页面可切回 deepseek/random/alternate）；讨论轮次默认 5（页面可调 1-10）
- **权衡**：Kimi 带思考、每篇较慢（约 6-10 分钟/5 轮）；作者选择质量优先；如嫌慢可降轮次或临时切 DeepSeek
- **体验**：讨论页已实时显示"当前模型正在思考（起草/评审/修订+轮次）"，避免误以为顺序错乱
