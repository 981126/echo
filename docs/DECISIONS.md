# 关键设计决策（DECISIONS）

> 记录重要技术决策与原因，防止后续 agent 重复质疑或改坏。新增决策追加编号 D-xxx。
> 编号说明：早期文档存在同号追加（如第二个 D-011/D-017/D-018），本文件用「D-xxx+」表示
> 追加在同号之后的演进决策，正文以年份标注区分；代码/历史文档引用的 D-023/D-026/D-027/D-028/D-030 均指本文同名条目，未变。

## D-001：单用户轻量单体架构
- **决策**：单进程 FastAPI 单体，不引入 Redis / 消息队列 / 微服务
- **原因**：单用户规模，NAS 资源有限，越简单越可靠
- **扩展路径**：模块化 + 适配器模式，未来加队列/拆分服务时业务逻辑不动

## D-002：SQLite 数据库（Alembic 为 tech-debt）
- **决策**：数据库用 SQLite + SQLAlchemy 2.x；schema 演进用 db.py 内**幂等轻量迁移**（建表后按需补列/建索引/回填）
- **原因**：单用户写入小、零运维、备份即拷文件；实际代码未落地 Alembic 脚手架（R-016 起用轻量迁移兜底），文档已更正，勿再按“已用 Alembic”编写
- **代价**：并发写受限（单用户无感）；未来多用户再评估

## D-003：LLM 适配器 + DeepSeek/Kimi 可插拔
- **决策**：所有 LLM 调用统一 OpenAI 兼容客户端（services/llm.py），模型名 env 可配；生成默认 Kimi，可切 deepseek/random/alternate
- **原因**：中文语气质量与成本可控；双模型交叉评审可压 AI 感（见 D-025/026）

## D-004：ASR 用阿里云录音文件识别（FileTrans 4.0）
- **决策**：转写用阿里云 FileTrans（`services/aliyun_filetrans.py`，CommonRequest RPC POP：SubmitTask/GetTaskResult 轮询）+ OSS 中转（`aliyun_oss.py`，预签名 URL，识别后删除临时文件）
- **交互（R-033）**：上传前 ffmpeg 抽音轨（16k 单声道 wav，imageio-ffmpeg 自带二进制）只传音频上云；上传/inbox **不自动转写**，编辑页「语音转文字」手动触发
- **验收**：E2E 实调 2026-09-05 通过（官方样例返回「北京的天气。」）；本地测试保持 mock

## D-005：长任务用 DB 任务表 + daemon 线程，不用队列
- **决策**：`background_tasks` 表 + tasks.py daemon 线程；结束自动写 `notifications`
- **原因**：单用户下 Redis/RQ 过度设计；DB 记录可留历史与状态

## D-006：前端 Vue 3 + Vite + Naive UI SPA
- **决策**：前端 Vue3 SPA（hash 路由），dev 5173 代理 8000；也可 build 后由 FastAPI 托管 dist
- **原因**：工作台交互多，SPA 体验好；Naive UI 按需引入、组件完整

## D-007：需求归档以文件为事实源（requirements/）
- **决策**：R-xxx.md 文件为事实源（git 留痕、AI 可读），DB 仅同步索引供 Web 展示
- **执行**：原文原样登记，反问/确认/结论随档；编号自动取当前最大 +1

## D-008：开发与运行分离（笔记本开发 / NAS Docker 运行）
- **决策**：代码在笔记本开发（.venv），NAS 只跑 Docker Compose 产物；数据目录挂载（当前 `echo_resource/`）

## D-009：WorkBuddy / 微信通道暂不接入
- **决策**：不进里程碑，列为未来扩展（推送走 ClawBot iLink，对话走 FastMCP 包成 MCP 连接器）

## D-010：项目命名 echo（回声）
- **决策**：寓意「复现作者声音」；包名 `echo`、库 `echo.db`、镜像/服务 `echo`、前端包 `echo-web`、env 前缀 `ECHO_`

## D-011：五维工程标准 + scripts/verify.sh 门禁
- **决策**：简单/易读/可靠/扩展/性能五维；门禁 = ruff + mypy + pytest(53 项离线) + 前端 lint/build + 文档存在性
- **原因**：项目长期由 AI 维护，可读性与可验证性是可持续前提

## D-012：需求反问机制（强制）
- **决策**：新需求必须先过 8 项反问清单（WORKFLOW.md），作者确认后才进 PRD/排期/代码
- **例外**：线上明显 bug 先定位根因直接修复并登记（2026-09 实践）

## D-013：视频导入双通道
- **决策**：Web 上传 + `inbox` 文件夹自动监听（watcher 10s 轮询，移入 videos 并建行；R-033 起不自动转写）

## D-014：风格样本检索用本地 TF-IDF（字符二元组）
- **决策**：语气一致性检索用本地 BM25/TF-IDF，不引入云端 embedding
- **原因**：单用户样本量小，本地零成本够用，少一个外部依赖

## D-015：AI 对话页权限边界
- **决策**：只读问答直接答；写操作（生成/改稿/删除）必须先经作者明确同意；系统提示词强制该边界

## D-016：主赛道/平台字段（演进为多选）
- **决策（早期 D-016 单选）**：每条视频一个主赛道 + 可选副标签 → **演进（2026-09，D-017+）**：`platforms`/`main_topics` 改为 JSON 多选，存量单值迁移为数组
- **口径**：看板/复盘/雷达按视频选中项各自聚合；统计为该集合下视频表现，不做权重拆分
- **注意**：改稿差异/人设学习不依赖平台赛道

## D-017：可靠性细节（必做）
- 每日流水线幂等（同日不重跑）；Web 手动触发；转写后 AI 校对；热点快照 30 天清理、指标全留、可归档

## D-018：移动端响应式适配
- **决策**：Web 做移动端响应式（手机浏览器可读/快速操作），不做 App；进入 M2 验收

## D-018+：封面由作者上传，不自动抽帧（2026-09）
- **决策**：封面 = 作者上传 jpg/png（存 covers/，videos.cover_path），不做 ffmpeg 自动抽帧
- **原因**：NAS CPU 抽帧重、作者本就人工选封面；「建议截取秒数/自动抽帧」列为未来扩展

## D-019：前端体验升级技术取向（R-015~R-018）
1. 视觉参考 seanhalpin.xyz 极简文艺，Naive UI + 系统字体栈 + 内联 SVG，无外部 CDN
2. 草稿正文用 **Markdown 为存储与编辑格式**（编辑器 + 渲染），不用 HTML 富文本——不破坏 AI 文本管线（diff/生成/学习）
3. 编辑器插图：上传存 uploads/，以 `/uploads/xxx` 相对 URL 写入 Markdown
4. AI 对话：多会话 + SSE 流式 + Markdown 渲染

## D-020：通知中心 = 任务表线程收尾落库 + 铃铛轮询（R-019）
- **决策**：后台任务 done/failed 自动写 `notifications`；前端铃铛轮询（5s）红点/列表/跳转/已读
- **原因**：内网单用户无推送基建，最简可靠

## D-021：全量风格学习 = 统计画像 + 表现加权样本注入（R-020/R-057/R-064）
- **决策**：生成时注入（1）非广告素材实时风格画像（口癖/句长/语气占比/标志性词）；（2）风格样本按「表现加权 × 时间衰减」去重取 top-k；（3）1-5 星打分回流
- **语料（R-064）**：提示词优化/每周重建用全量素材按「点赞率/互动/时间衰减」加权取前 16 条，不再只看最新视频
- **隔离**：广告（is_ad）全程不进人设/风格学习

## D-022：AI 提示词版本化存库（R-021）
- **决策**：默认提示词仍留代码常量，首次启动 seed 入 `ai_prompts` v1；运行从 DB 读 enabled 版本；编辑/优化=另存新版本（enabled/candidate），可回滚；候选不自动启用

## D-023：AI 是学习引擎，提示词只是方向盘（R-022）
- **决策**：更像作者主要靠数据闭环；提示词自动优化**永不直接启用**（候选制 + 每 3 条素材节流 + 启用前 diff + 金样本自测提示）

## D-024：双模型讨论生成（R-023）
- **决策**：LLM 统一 OpenAI 兼容适配；生成策略可切（固定/随机/轮流）；每篇「初稿 + 5 轮互评修订」逐轮写 draft_discussions；任一方不可用自动退单模型

## D-025：默认生成组合 = Kimi 起草/修订 + DeepSeek 评审（R-023 实测）
- **决策**：generation_model=kimi（可切 deepseek/random/alternate）；轮次默认 5（可调）
- **权衡**：Kimi 带思考较慢（约 6-10 分钟/篇），质量优先

## D-026：平台数据统一走 TikHub（R-027/R-029）
- **决策**：抖音/B站/小红书主页、作品、指标、评论统一经 TikHub API（Bearer `ECHO_TIKHUB_API_KEY`），不做官方开放接口/自研爬虫
- **护栏**：每日请求预算默认 2000（页面可调，Kv 覆盖），超限停止本轮并通知；失败隔离 + 通知；sync_jobs 留痕
- **真实化**：2026-09-06 起 real 模式线上联调通过

## D-027：云端作品与本地素材分离建模（R-027/R-029）
- **决策**：云端作品独立 `platform_posts` + `platform_post_stats`（按天快照）+ `platform_post_comments` + `creator_account_snapshots` + `sync_jobs`；不塞进 `videos`
- **视频策略**：默认不下载视频（省额度，D-027 代码注释同义）；封面下载本地；需要时手动「转本地素材」生成 videos 记录
- **绑定**：videos 仅加 creator_id/platform_post_id/work_id；编辑保存可写回绑定/合并的平台帖子（标题/广告/价格/时间）

## D-028：多主博主 + 对标，切换整套随动（R-029）
- **决策**：多主博主数据完全隔离（人设/素材/草稿/打分/复盘按主博主归属）；主博主下可挂多个对标；切换带确认弹框
- **对标边界**：对标只做数据对比 + 风格参考卡，**永不进入主博主学习语料/提示词优化**

## D-029：存量数据清库策略（R-029）
- **决策**：实施 M13 时只清 DB 业务数据（先整库备份），本地视频/封面文件保留；首个主博主由作者页面手动创建，不预置

## D-030：选题池人工挑选，不自动推送（R-028）
- **决策**：选题池来源 = 各平台热点（TikHub 热搜，R-065）+ 主博主评论 + 对标评论；进池供人工挑选，不自动推送生成

## D-031：素材合并/拆分与文件命名（2026-09-05，原 D-011 追加）
- 文件命名：`{平台前缀}-{主标题}-视频/封面.{ext}`（去除 #话题、清洗、重名 -2/-3）
- 合并卡片：多平台帖聚合同一 work，共用**一个**本地视频文件（不复制）
- 拆分卡片：仅解绑 work（work_id=null），不复制文件、不断开 local_video_id
- 编辑一致性：保存本地素材写回绑定/合并平台帖子；详情接口本地缺字段用平台数据兜底

## D-032：系统时间统一北京时间（R-066，2026-09-06）
- **决策**：core/timeutil.now/today 为唯一时间来源（默认 Asia/Shanghai，`ECHO_TIMEZONE` 可覆盖）；所有模型默认时间与手动赋值点统一；存量 UTC 时间一次性 +8h（db.py 幂等迁移标记）
- **原因**：历史用 datetime.utcnow 存 UTC，展示差 8 小时

## D-033：评论点赞 Top50 入库 + 合并卡全平台同步（R-067，2026-09-06）
- **决策**：数据源评论结构化 `CommentData(text, likes, user_nick)`；`platform_post_comments` 加 likes；入库按点赞降序保留每平台 Top50、文本去重（保留更高赞）；评论读接口按点赞降序返回
- **卡片同步**：云端合并卡新增 work 级同步（遍历合并作品全部平台帖，不再只同步 cloudPosts[0]）；本地绑定卡同步后前端刷新；同步链路统一拉评论
- **原因**：原评论无点赞数无法 Top50；合并卡只同步首平台是 R-067 前缺陷

## D-034：模式配置护栏——非法值启动报错（R-068，2026-09-06）
- **决策**：`.env` 注释黏连（`TIKHUB_MODE=real# mock | real`）曾导致静默回退 mock、用假数据覆盖真实指标；修复 `.env` 并加 `normalize_mode`：剥离 `#` 注释、白名单校验，非法值**启动即抛错**
- **原因**：宁可启动失败也不静默写假数据

## D-035：卡片同步按钮 loading 用唯一 key（R-069，2026-09-06）
- **决策**：素材库「同步中」按卡片唯一 key（`v<id>`/`w<id>`/`p<id>`）判断，不用裸数字 id
- **原因**：合并作品 work_id 与单条云端 post id 可能同号（如都=1），裸 id 会导致点 A 误触发 B 按钮状态

## D-036：同步前 20 条 + 实时进度条（R-070，2026-09-06）
- **决策**：daily 同步默认 top_n 10→20；sync_jobs 加 progress_done/progress_total/progress_note，同步中按作品原子累加；博主页 1s 轮询 jobs 显示进度条（全量阶段总数未知用流动动画）
- **原因**：作者要覆盖前 20 条；长同步（尤其 B站补全）需要可见进度

## D-037：API/DATABASE 文档自动生成（R-071，2026-09-06）
- **决策**：`docs/API.md` 由 FastAPI OpenAPI 生成（92 路由）、`docs/DATABASE.md` 由 SQLAlchemy 模型元数据生成（26 表 + 人工注释），改接口/表结构后重新生成，不手改结构部分
- **配套**：全量重写 AGENTS/README/PRD/PRODUCT/ARCHITECTURE/DESIGN/milestones/WORKFLOW/QUICKSTART/GLOSSARY/FAQ，以代码为准消除过期/错误表述

## D-038：素材卡「同步数据」补齐视频+转写（R-077，2026-09-06）
- **决策**：卡片「同步数据」在原有指标/评论同步后，检查该卡是否有本地视频文件与已完成转写；缺视频按平台优先级（抖音→小红书→B站）下载低清视频（下载成功才建本地素材行，不留死占位），缺转写则自动跑现有 ASR 流水线（import_video_task）；全部后台任务 + 通知，前端提示并轮询刷新。
- **范围**：不区分博主，所有素材卡一致；常规平台同步（D-027）仍不自动下载。
- **现状（受第三方限制）**：抖音（bit_rate 低档直链）、小红书（video_info_v2.media.stream.h264 master_url）实测可下载；B站 TikHub `fetch_video_playurl` 等端点当前线上 404（key 未开通/服务端下线），代码已按 SDK 参数接好，接口恢复即用；纯 B站作品会明确提示「无可用视频源」，不做假下载。
