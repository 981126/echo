## 一、需求背景

### 1.1 现在的情况（小白也能看懂）

项目里很多功能靠 AI 完成：生成口播稿、洗稿、人设提取、视频复盘、选题、AI 对话、转写校对……每个功能在调用 AI 时都要先给它一段「提示词」，告诉它「你是谁、要干什么、按什么格式输出」。

现在提示词分散在两个地方：

| 位置 | 数量 | 作者能看到/能改吗 |
|---|---|---|
| 数据库表 `ai_prompts`（「AI 设置 → 高级 → 功能提示词」页面） | 10 个功能 | ✅ 能看、能改、有版本、有 AI 优化候选、有金样本评分 |
| 直接写在 Python 代码里 | 21 个产品系统提示词 + 11 条输出契约 + 17 条固定规则 + 25 条用户消息模板 | ❌ 页面看不到、改不了；要改必须改代码、重启后端、重新发版 |

也就是说：**「AI 设置」页看起来像「所有提示词都能在这里管」，实际上只覆盖了 10/31 个功能。**

### 1.2 这会带来什么问题

1. **改一句话要发一次版**：洗稿评审怎么挑刺、选题怎么选、复盘建议怎么写、对话工具怎么用，这些都写在代码里；作者想微调只能找开发改代码。
2. **同一个功能两套提示词，页面管不到**：比如“视频复盘归因”在表里有 key，但“视频复盘按指标优化建议”是另一段写死的提示词，页面完全看不到；两段都叫“视频复盘”，很难分清谁管什么。
3. **没有中文说明**：现有页面只有「生成脚本」「人设逐篇提取」这类短名字，没有「这个提示词用在哪个页面/后台任务、干什么用的」说明；22 条写死的产品提示词连名字都没有。
4. **版本/回滚/评测能力只有 1/3 的功能享受**：新增提示词改了就是改了，改坏了只能回滚代码。
5. **启动兜底是失效的**：设计上「某个功能没有启用版本时自动用代码默认补一条」的函数（R-231）实际没挂到启动链路，新增 key 只能手写数据库迁移脚本，容易漏。

### 1.3 这次要做的事

把**所有会作为 AI 指令发出去的「系统提示词」**理出来（包括页面上已配置的 10 个），统一存到一张新表里。这张表每行有一条提示词，并有一列**中文说明**写清「它用在哪个模块/功能、干什么用的」。以后 AI 调用统一从这张表读提示词；页面能把全部提示词按模块列出来，可改的能改、程序固定的只读展示。

## 二、想要实现的目标

1. **一处看全**：新建「AI 提示词注册表」，把 32 条产品系统提示词（33 个盘点单元中广告判定拆两行）+ 2 条内部自检探针 + 11 条程序固定契约全部登记，每条都有中文名、所属模块（中文）、用途说明（中文）。
2. **以后读表**：所有 AI 调用的系统提示词改为从数据库读取；代码里的常量只作为「首次种子」和「数据库读不到时的兜底」，不再直接决定线上行为。
3. **页面可管**：`/prompts`（AI 设置 → 高级 → 功能提示词）改成按模块分组的提示词清单，每行能看到中文名、模块、用途说明、是否可编辑、当前版本；可编辑的沿用现有「编辑保存 / 版本历史 / 候选 / 评测」能力。
4. **只读有边界**：程序固定的 JSON 输出契约、内部自检探针只读展示，页面不能改，防止把程序解析契约改坏。
5. **不破坏现状**：现有 10 个功能的已启用版本内容逐字保留；新表/新接口对旧前端向后兼容；数据库不可用或表未初始化时，行为自动回退到代码默认（不会出现「提示词变空、AI 全乱」）。
6. **补齐兜底**：启动时幂等补种「注册表里登记了但库里没有的提示词」，以后新增提示词不用再手写迁移脚本，也不会出现「页面显示无启用版本」。

## 三、页面数据来源

本需求只改「AI 设置」页里的提示词区域，不新增页面、不引入第三方数据。

| 页面区域 | 数据来自哪里 | 说明 |
|---|---|---|
| 提示词清单（中文名/模块/用途/类型/当前版本/是否有候选） | 新表 `ai_prompt_defs`（元数据）+ `ai_prompts`（当前启用版本号） | 一次 `GET /api/prompts/keys` 全量返回 |
| 当前启用正文（可编辑文本域） | `ai_prompts` 中该 key 最新 `status=enabled` 行的 `content` | 现有逻辑不变 |
| 历史版本列表 | `ai_prompts` 该 key 全部版本（按 version 倒序，页面展示最近 30 条） | 现有逻辑不变 |
| 候选版正文 / 是否有候选 | `ai_prompts` 中 `status=candidate` 的行 | 现有逻辑不变 |
| 候选评测分数（候选 vs 当前） | `prompt_evals` 最近一次评测 | 现有逻辑不变 |
| 版本效果对比（生成脚本专用） | 按 `drafts.prompt_version` 聚合草稿 / 反馈 | 现有逻辑不变，仅 generation 有数据 |
| 程序固定契约（只读区） | `ai_prompt_defs` 中 `category=contract` 行的 `default_content`（启动时从代码 `prompt_contract` 同步镜像） | 新增只读展示 |
| 作者输入 | 只有「提示词正文」文本域里的编辑内容；保存时整段提交 | 不涉及其它人工录入 |

**不读的数据**：模型 Key、预算、人设页的运行上下文（禁用词/风格范本/金句/红线）都不进提示词正文，也不改；这些仍是「AI 设置基础 tab」和人设页的职责。

## 四、功能需求

### 4.1 新增数据表：AI 提示词注册表 `ai_prompt_defs`

一张表，一行 = 一条提示词（不是版本）。字段和含义：

| 字段 | 类型 | 中文含义（小白版） |
|---|---|---|
| `id` | 整数主键 | 自动编号 |
| `key` | 文本（唯一） | 提示词唯一代号，例如 `generation`、`rewrite_critic`；程序按它取提示词 |
| `title` | 文本 | 中文名，例如「洗稿讨论-评审」 |
| `module` | 文本 | 所属模块英文代号，例如 `rewrite` |
| `module_label` | 文本 | **所属模块中文名**，例如「对标洗稿」 |
| `purpose` | 长文本 | **这个提示词用于哪个模块功能、干什么用的**（中文，1~3 句，写清输入→输出） |
| `category` | 文本 | 类型：`system`=系统提示词（可编辑）/ `contract`=程序固定输出契约（只读）/ `probe`=内部自检探针（只读） |
| `editable` | 是/否 | 页面上能不能改 |
| `optimizable` | 是/否 | 页面上能不能点「AI 优化候选」和「金样本评测」 |
| `llm_feature` | 文本 | 调用时用的模型路由功能名（决定用模型1/2、超时预算） |
| `entry` | 长文本 | 触发入口中文说明，例如「对标洗稿后台任务 / 草稿讨论」 |
| `default_content` | 长文本 | 代码里的默认正文（首次种子、以及页面「恢复默认」的基准） |
| `code_ref` | 长文本 | 代码位置（文件:行号/常量名），方便回溯 |
| `sort_order` | 整数 | 页面展示顺序 |
| `is_active` | 是/否 | 是否启用（默认是；下线提示词时不必删数据） |
| `created_at` / `updated_at` | 时间 | 创建/更新时间 |

**和现有 `ai_prompts` 的关系**：`ai_prompt_defs` 管「有哪些提示词、叫什么、给谁用、默认长什么样」；`ai_prompts` 继续管「某条提示词的第几版正文、当前启用哪版」。两者用 `key` 关联。

### 4.2 页面改造：「AI 设置 → 高级 → 功能提示词」

**位置不变**（侧栏「AI 设置」→ 顶部「高级」tab → 下方「功能提示词」卡片），形态从「一个下拉框 + 单条详情」改为「按模块分组的清单 + 单条详情」。

改动点：

1. **提示词清单（新）**：按 14 个模块分组（脚本生成 / 对标洗稿 / 对标分析 / 人设引擎 / 素材导入 / 改稿学习 / 视频复盘 / AI 对话 / 选题灵感 / 内容机会 / 素材检索 / 草稿元信息 / 提示词优化 / 系统自检），每行显示：
   - 中文名（如「对标洗稿初稿」）
   - 模块中文名（如「对标洗稿」）
   - 用途说明（`purpose`，灰色小字，一行省略、悬停看全文）
   - 类型徽章：可编辑 / 程序固定（只读）/ 内部探针
   - 当前启用版本（如 `v3`；只读项不显示版本）
   - 「有候选」标记（现有逻辑）
2. **选中后详情（沿用现有卡片，补充字段）**：
   - 标题区显示：中文名 + 模块 + 类型；用途说明完整显示；触发入口（`entry`）一行小字。
   - 可编辑项：正文文本域 + 「保存为新版本并启用」按钮；`optimizable=true` 时显示「AI 基于真实样本优化（候选）」；候选卡片、评测、版本效果、历史版本全部沿用现有能力。
   - 只读项（契约/探针）：正文只读展示（灰色/不可输入），不显示保存与优化按钮，显示一句「程序固定，不能在这里改」。
3. **程序固定契约区（新）**：清单下方一个可折叠区「程序固定输出契约（只读）」，列出 11 条契约：中文名 + 用途 + 正文。只读，不提供编辑。
4. **空数据表现**：清单接口返回空 → 显示「提示词清单尚未初始化，后端启动会自动补种；若持续为空请检查数据库迁移」+「重新读取」按钮。
5. **加载/失败表现**：
   - 加载中：清单区显示骨架屏（不整页转圈）。
   - 接口失败：顶部 toast 报错，保留上一次成功的数据（不清空）。
   - 保存失败 / 未知 key：toast 显示后端原因，不关闭编辑框。
   - AI 优化未开放：按钮直接不显示（不是点了才报错）；若直接调接口，返回 400 并提示「该提示词暂未开放 AI 优化」。
   - 只读项被直接调保存接口：返回 400「该提示词为程序固定，不可编辑」。
6. **移动端**：清单在窄屏改为纵向列表（不横向溢出），详情卡片保持整宽；不做新动效（沿用站点现有 hover/按下反馈）。

### 4.3 运行时行为（功能需求）

1. **统一读表**：所有产品 AI 调用的系统提示词改为 `get_prompt(key)` 从数据库读（优先级：`ai_prompts` 当前启用版本 → `ai_prompt_defs.default_content` → 代码默认常量 → 空串并记警告）。
2. **启动补种（幂等）**：后端每次启动检查注册表：缺记录就按代码默认补登记；登记了但 `ai_prompts` 没有启用版本的，自动种一条 v1 并启用（note 写「系统默认（R-255 统一入库补种）」）。以后新增提示词不再需要手写迁移脚本。
3. **不覆盖作者改过的内容**：已有启用版本（现有 10 个 key）逐字保留，启动补种只补缺失、不重写已有。
4. **一次性修正 `video_review`**：该功能现在库里是 54 字的精简占位句，不是代码里真正的完整提示词。升级时把它另存为「代码完整默认版」并启用，旧版归档可回退；用一次性标记保证只执行一次。
5. **契约不入版本、不参与编辑**：11 条输出契约由程序在 AI 优化候选末尾自动拼接、并用于候选自检，属于程序解析契约；表里只做只读展示与审计，运行时不从表读（防止页面改动破坏 JSON 解析）。

### 4.4 新增提示词的默认开放程度

| 对象 | 数量 | 页面可编辑 | AI 优化/评测 |
|---|---:|---|---|
| 现有已入库的 10 个功能提示词 | 10 | ✅ 保持 | ✅ 保持 |
| 新增的产品系统提示词 | 22 | ✅ 可编辑（保存新版本即生效、可回滚） | ❌ 先关闭（`optimizable=false`），后续逐条开放 |
| 内部自检探针 | 2 | ❌ 只读展示 | ❌ |
| 程序固定输出契约 | 11 | ❌ 只读展示 | ❌ |

> 说明：新增提示词先不开放 AI 优化，是因为「优化」需要为每个 key 准备专属语料、输出契约、金样本评测口径（R-129 机制），22 条一次补齐风险大；先让作者能看能改，再按需逐条补优化能力。页面不显示优化按钮，直接调接口返回 400。

### 4.6 本次不做什么（边界）

1. **不改任何一条提示词的正文内容**（除 `video_review` 恢复完整版）；不重写措辞、不调效果。
2. **不把用户消息模板改成「表里的模板」**：它们要拼人设/素材/证据等运行时数据，改成表模板需要占位符引擎，风险高收益低；本次只在设计文档登记清单。
3. **不改 JSON 输出契约与解析逻辑**：契约仍由代码固定，表里只读展示。
4. **不开放新增 22 条提示词的 AI 优化/评测**（见 §4.4）。
5. **不改模型路由/预算/人设页/对话工具**。
6. **不做权限系统**：仍是单用户 + access token，无角色区分。
7. **不删旧的 `ai_prompts` 表、不改其版本语义**。
