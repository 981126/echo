## 现状核对（2026-11-04 代码检查 + 运行中进程取证）

1. **所有 TikHub 请求共用一个进程级 httpx Client**：`backend/app/core/http.py` 按 `base_url + follow_redirects` 缓存 Client（R-241），连接池上限 `httpx.Limits(max_connections=16, max_keepalive_connections=8)`。
2. **httpx 默认 `trust_env=True`，在 macOS 上会读取「系统代理」**：即使后端进程环境变量里没有 `HTTP_PROXY`，httpx 也会通过 `urllib.request.getproxies()` 读到系统代理（本机为 Clash `127.0.0.1:7890`）。TikHub 请求实际走 HTTP CONNECT 隧道（`httpcore.HTTPProxy`）。
3. **同步并发会瞬间打满连接池**：手动「同步 Top15」会同时启动 12 个账号同步任务（`all_top15` 拆成 12 个平台同步子任务）；单账号内还有 `sync_post_concurrency=5` 的作品/评论并发。峰值约 12 × 5 ≈ 60 个 TikHub 请求同时涌向 16 连接的共享池。
4. **httpcore 1.0.9 的代理隧道存在槽位泄漏缺陷（已在运行进程实证）**：当 CONNECT 隧道建立后、TLS 升级阶段失败/超时时，`TunnelHTTPConnection` 不会关闭并回收内部连接——内层连接停在 ACTIVE 状态、`_connected=False`、socket 已关闭（fd=-1），连接池永远不把它判为「已关闭」，该槽位永久泄漏。
5. **泄漏累积到 16/16 后池永久坏死**：此后每个 TikHub 请求都要等 20 秒池超时，重试 4 次后报 `TikHub 请求失败（已重试 3 次）: PoolTimeout`（单次任务约 94 秒），**只有重启后端能恢复**（连接池在内存里）。
6. **实锤时间线**：
   - 11-02 07:34 最后一次成功的同步任务；11-02 09:00 起看板刷新开始出现 `PoolTimeout`；此后两天的定时同步（06:00/17:00）、11-04 19:00 的 Top15 同步（12 个账号）和所有看板更新全部失败。
   - 看板账号诊断缓存停在 `2026-11-01 11:36`，作品指标停在 `2026-11-02 01:05`。
   - 2026-11-04 19:29 重启后端后，19:31 一次真实「更新数据」5.5 秒成功（此前同样操作 94 秒后失败），诊断时间与看板 KPI 恢复更新。
7. **已排除的其它原因**：TikHub API Key 有效（当日用量约 77/2000，远未用完）；抖音创作者 Cookie 状态 `valid`；用同一 key/cookie 在独立进程直连 TikHub 真实接口 1.77 秒成功。**唯一问题在后端进程内的连接池**。
8. **对照「为什么每次切页面回来都重新更新」**：前端进入看板时会对 `needs_refresh`（账号诊断 >24h）或 `stale`（作品 >6h）自动发起后台刷新（同目标 10 分钟最多一次）。因为 TikHub 一直失败，数据永远处于过期状态，所以每次离开再回来都会再自动刷新一次并再次失败；此外 React Query 每次页面重新挂载也会重新拉取接口、曲线会再淡入一次（设计如此，非本需求修复对象）。

## 一、需求背景

数据看板、作品分析、博主管理/素材库同步的数据**全部来自 TikHub 第三方接口**。从 2026-11-02 起，后端进程内所有 TikHub 请求都报 `PoolTimeout`：不是 TikHub 挂了，而是后端自己「打电话的线路池」被 16 个卡死的代理隧道占满，电话再也打不出去。结果：
- 看板「数据更新至」停在 3 天前，KPI/曲线不再更新；
- 作品分析、视频复盘拿不到新指标；
- 每日定时同步、手动「同步 Top15」全部失败（今天 12 个账号 0 成功）；
- 只能人工重启后端恢复，且下次并发高峰/代理抖动时会再次发生。

这是**稳定性缺陷**而非新功能：需要让 TikHub 访问层不再被单次上游抖动永久卡死，并且不再把 60 个并发塞进 16 条线路。

## 二、想要实现的目标

| 目标 | 可验收标准 |
|---|---|
| 连接池不再被永久占死 | 连续触发看板「更新数据」2 次均成功；每日同步 12 个账号成功、无 `PoolTimeout` |
| 出现 PoolTimeout 能自动恢复 | 单测：mock 一次 `PoolTimeout` → 自动重置共享连接池 → 同一任务后续重试成功，无需重启后端 |
| 降低代理隧道依赖 | TikHub 默认**直连**（不跟随系统/环境代理），实测直连真实接口 1.77 秒可用；保留 env 开关以兼容必须走代理的网络环境 |
| 并发不超过连接池/上游承受能力 | 所有 TikHub 请求受进程级全局并发上限约束（默认 8）；单测并发 20 请求断言同时在途 ≤ 上限 |
| 不影响现有功能 | mock 模式、其它服务（DeepSeek/联网搜索/CDN）的代理行为、接口契约、表结构、预算计费语义均不变；`verify.sh` 全绿 |

**明确不做**：
- 不改前端页面/按钮/字段，不改任何 API 路径、请求/响应字段、错误码；
- 不改数据库表结构（不新增表/列/索引，无 Alembic revision）；
- 不改 TikHub 业务响应解析、限速令牌桶（`ECHO_TIKHUB_RATE_LIMIT`）、重试次数与退避序列、每日预算口径；
- 不做多进程/多实例连接池治理（当前单进程 uvicorn 部署）；
- 不升级 httpx/httpcore（0.28.1/1.0.9 均为当前最新版，且该缺陷需应用层规避）；
- 不把 TikHub 失败静默改成 mock 假数据。

## 四、功能需求（无页面/字段变更，均为后端行为）

### 4.1 TikHub 默认直连（不跟随系统/环境代理）

- 行为：TikHub 的 httpx Client 改为独立创建（`trust_env=False`），请求直接连 `https://api.tikhub.io`，不再经过 macOS 系统代理/环境变量代理，从根上避开 CONNECT 隧道泄漏缺陷。
- 兼容开关：新增 `ECHO_TIKHUB_USE_PROXY`（默认 `0`/关闭）。设为 `1` 时恢复旧行为（跟随系统/环境代理），供网络必须走代理的环境使用。
- 其它服务不变：DeepSeek、联网搜索、CDN 等 Client 仍为 `trust_env=True`，行为与现在完全一致。
- 失败表现：直连不可用时，任务按现有逻辑失败并提示 `TikHub 请求失败…`；保留上次成功数据，不伪造、不静默切换 mock。

### 4.2 TikHub 全局并发上限

- 行为：所有线程（看板刷新、作品刷新、定时同步、手动同步）发出的 TikHub 请求共享一个进程级并发闸门，默认同时最多 **8** 个在途请求，其余排队等待；排队不报错、不消耗预算。
- 配置：新增 `ECHO_TIKHUB_MAX_CONCURRENCY`（默认 8，允许 1~64；非法值按默认 8 处理）。
- 目的：即使「同步 Top15」同时拉起 12 个账号任务，也不会把 16 连接的池与上游代理打爆；配合 4.1 后代理压力也不再存在。
- 失败表现：排队时间过长时由现有请求超时/重试兜底；页面仍按现有「更新中…」动效展示进度，不新增 UI。

### 4.3 PoolTimeout 自动恢复（自愈）

- 行为：任一 TikHub 请求在等待连接池时抛 `httpx.PoolTimeout`，立即**关闭并丢弃当前共享 Client**（下次请求自动重建新连接池），然后按现有 4 次重试序列继续重试；同一请求最多触发 1 次重置。
- 边界：重置时可能让极少数其它在途 TikHub 请求失败一次（它们各自会重试），但换来整个进程不再需要人工重启。
- 失败表现：重置后仍失败 → 最终错误文案保持现状（`TikHub 请求失败（已重试 3 次）：…`），任务失败、页面保留上次成功数据；预算按实际发出的请求次数计，语义不变。
- 观测：重置发生时写一条 warning 日志（含接口路径、第几次尝试），便于判断是否仍在频繁触发。

### 4.4 可配置项（新增 2 个，均有默认值，不改 `.env` 也能运行）

| 配置项 | 默认值 | 含义 |
|---|---|---|
| `ECHO_TIKHUB_USE_PROXY` | 关闭（直连） | TikHub 是否跟随系统/环境代理；`1`=跟随即旧行为 |
| `ECHO_TIKHUB_MAX_CONCURRENCY` | 8 | TikHub 全进程并发上限（1~64） |

### 4.5 空数据 / 失败表现汇总

| 情况 | 页面表现 |
|---|---|
| TikHub 正常 | 与现在一致：任务完成后数据/时间刷新 |
| TikHub 单次抖动 | 自动重试 / 自动重置连接池后恢复，用户无感（除非确实失败） |
| TikHub 持续不可用 | 任务失败 toast（现有文案）、页面保留上次成功数据 + 现有警告条；不会白屏、不会显示假数据 |
| 预算用完 | 现有「今日 TikHub 请求预算已用完」提示，不发起新请求 |

## 五、边界与默认结论（作者已确认采用推荐方案）

1. **TikHub 默认直连 + 保留 `ECHO_TIKHUB_USE_PROXY` 开关**（推荐方案；实测直连可用）。
2. **允许 PoolTimeout 时重置共享连接池**（极端情况下极少数在途请求失败一次，优于永久卡死直到重启）。
3. **全局并发上限默认 8**（连接池 16 的一半，稳定优先；可配置）。
4. 不改连接池上限 16（在「直连 + 并发 ≤8」下已足够；避免影响其它服务与引入新变量）。
5. 本次只修「连接池卡死」这一个根因，不顺手改同步业务逻辑；若后续仍偶发失败，再单独立项分析代理稳定性。

## 六、用户故事

1. 作为作者，我切回数据看板时希望看到最新数据，而不是每次都在「更新中 → TikHub 请求失败」之间反复；TikHub 或代理抖动时系统能自动恢复，不需要我重启后端。
2. 作为作者，我点「同步 Top15」同时同步 12 个对标账号时，不希望把后端连接池打爆，导致一整天所有看板/同步数据都拿不到。
3. 作为作者，我点任意页面的「更新数据」按钮时，按钮的用途与位置不变，只是成功率恢复、等待时间恢复为几秒级。
4. 作为维护者，我希望从日志能直接看到「连接池被重置了几次」，从而判断是否需要换网络/代理。

## 七、验收标准

1. **真实联调**：看板「更新数据」连续 2 次成功、单次 <30 秒；`diagnosis_at` 与「数据更新至」正常前进；作品分析「更新数据」成功。
2. **自动恢复**：单测模拟一次 `httpx.PoolTimeout` → 断言触发一次连接池重置且后续重试成功；模拟连续 PoolTimeout → 仍按现有 4 次重试后失败，不无限重试。
3. **并发上限**：单测并发 20 个 TikHub 请求（mock HTTP）→ 断言峰值同时在途 ≤ 配置上限；上限配置为 2 时断言 ≤2。
4. **开关**：`ECHO_TIKHUB_USE_PROXY=0` 时 TikHub Client 为直连（`trust_env=False`）；`=1` 时跟随系统/环境代理；其它服务不受影响。
5. **回归**：`scripts/verify.sh` 全绿（ruff + mypy + pytest + 前端 lint/build + 文档一致性）；mock 模式原有测试全部通过。
6. **手工点检**：手动触发一次「同步 Top15 / 每日同步」，12 个账号同步无 `PoolTimeout`；看板数据新鲜时切页不再自动发起刷新。

## 八、实施后预期指标

- TikHub 任务成功率：从 0%（11-02 09:00 后持续全失败）恢复到正常；
- 看板「更新数据」耗时：约 5~10 秒（对照 2026-11-04 重启后实测 5.5 秒）；
- 连接池泄漏：不再需要人工重启即可自愈；
- 并发峰值：TikHub 在途请求 ≤8。
