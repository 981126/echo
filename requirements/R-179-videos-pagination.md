# R-179 素材库加载太慢：分页 + 滚到底自动加载下一批（要「感觉不到加载」）

- **日期**: 2026-09-28
- **状态**: ✅ 已完成（2026-09-28，M168）
- **关联**: `frontend_v2/src/pages/videos/index.tsx`、`frontend_v2/src/pages/videos/material-card.tsx`、`backend/app/api/videos.py`、`backend/app/api/works.py`、`backend/app/services/works_service.py`、`backend/app/main.py`（/covers 静态托管）；R-165（素材库卡顿优化）、R-163（同步提速）

## 原文（作者原话，未改动）
> 素材库页面还是 加载太慢了，应该分页，每次加载20条，快划到底自动加载下一批数据，尽量让用户感觉没有加载的感觉

## 实测（冷缓存，浏览器探针，不是猜的）
| 指标 | 实测值 | 说明 |
|---|---|---|
| 首张卡片出现 | **1208 ms** | 之后仍有 616 ms 主线程长任务 |
| `GET /api/works` | 618 条 / **1.57 MB** / 227 ms | 页面**全量**拉取，其中 564 KB 是 `posts` 嵌套字段 |
| `GET /api/videos?limit=500` | 82 条 / 46 KB / 16 ms | 页面写死 `limit=500` 全量拉 |
| 首屏已加载封面 | **28 张 / 13.15 MB**（均 470 KB/张） | 封面上传时**原图直存、不压缩、无缩略图** |
| 封面库整体 | 1766 张 / avg 191 KB / p90 503 KB / max 1 MB / 共 **330 MB** | `/covers` 直接静态托管原图 |
| DOM 节点 | **24 262** | 本地 82 + 云端 618 合并去重后一次性渲染 |
| 12s 内请求数 | 124 | 图片为主 |

**结论**：慢不只是「一次拿多了」，而是三件事叠加——① 首屏全量拉 `/api/works`（1.57 MB）+ 全量渲染（24k DOM、616 ms 长任务）；
② 封面**原图直出**（首屏就 13 MB，即使分页到 20 条，按现在的图也会再下 ~9 MB）；③ 筛选全在前端内存里做，数据量再涨会更卡。

## 反问（待作者确认，按反问清单）
1. **分页口径**：素材库现在是「本地素材 + 云端作品」合并去重、按日期倒序展示（约 700 张卡）。分页做在
   **服务端合并后的统一列表**上（筛选/搜索一并下推到服务端，行为和现在完全一致），还是只给本地素材分页（云端仍全量）？
2. **加载节奏**：每批 20 条（你定的）；触发点用「距底部约 1 屏就预取下一批」（滚到底前数据已经到了，才有『没加载』的感觉）
   还是「滚到最底才请求」？要不要保留页码/跳页（现在没有，建议不做）？
3. **「无感」三件套**（可多选）：① 预取下一批 ② 骨架/占位卡（不动布局、不跳版）③ 切筛选时先留住旧列表再刷新 ④ 到底部的细微加载指示。
4. **封面缩略图（关键，实测首屏 13 MB）**：是否允许后端按需生成缩略图并落缓存（例如 `/covers/x.jpg?w=400`，单张 ~25–40 KB，
   首屏 20 张从 ~9 MB 降到 ~0.6 MB；原始大图保留不动）？用什么生成——新增 Pillow 依赖（推荐，最稳）还是复用已有的 ffmpeg？
   还是这轮先不做（那样分页后仍会明显慢）？
5. **筛选/搜索与多选**：筛选（平台/状态/标签/点赞/关键词）与「共 N 个素材 · 筛选后 N 个」计数是否也都走服务端分页统计？
   「多选」批量操作是只作用于**已加载的批次**（推荐）还是要「全选所有筛选结果」？
6. **返回态**：打开素材抽屉/弹窗再关闭、或从别的页面切回来时，要不要保持滚动位置与已加载批次（推荐保持）？
7. **动效（R-175 必问）**：新批次卡片的入场（骨架淡出 → 卡片淡入，禁止从 `opacity:0` 起步）、底部加载指示是否要做？做成什么样？
8. **优先级**：R-178（讨论留痕显示真实模型，已确认待开工）与 R-179（本需求）谁先做？

## 确认结论（作者 2026-09-28 逐项选择）
1. **分页口径**：服务端**统一列表**分页——本地素材 + 云端作品先按现有规则合并去重，再统一排序分页；筛选/搜索/计数一并下推服务端。
2. **加载节奏**：每批 **20** 条；**距底部约 1 屏就预取下一批**；不做页码/跳页。
3. **无感手段**：**四项全要**——① 预取下一批 ② 骨架/占位卡（尺寸与真卡一致、不跳版）③ 切筛选/搜索先留住旧列表再刷新 ④ 底部细微加载指示。
4. **封面缩略图**：**新增 Pillow**，后端按需生成缩略图并落缓存（`/covers/x.jpg?w=400`，~25–40KB），原图保留不动。
5. **筛选/多选**：筛选 + 搜索 + 计数**都走服务端**；「多选」批量操作**只作用于已加载批次**（不做跨页全选）。
6. **返回态**：保持滚动位置与已加载批次（抽屉/弹窗关闭、跨页返回都不重拉不闪）。
7. **动效**：骨架淡出 → 卡片淡入 `0.85 → 1` + 轻上移 8px（不动布局、不跳版），底部细微加载条只在真等待时出现。
8. **优先级**：R-178 与 R-179 **两个一起做、一起交**（各自一个 commit）。

## 补充实测（决定实现方式）
- `list_works` 194 ms 的构成（cProfile）：`post_item` ×1172 = 211 ms，其中 **`db.get(Creator)` N+1 1172 次 = 118 ms**、
  `build_platform_page_url` → `json.loads(raw)` **×2344 = 73 ms**（每条重复解析两次）。→ 与分页一起做这处瘦身，单批才可能几十毫秒。
- 封面来源：618 条云端作品的 `cover` **全部是本地 `/covers/*.jpg`**（`posts[].cover_url` 全空）→ 缩略图能覆盖本地 + 云端两类卡片。
