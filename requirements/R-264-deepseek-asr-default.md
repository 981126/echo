6. **数据**：`transcripts.asr_provider='deepseek'`、`asr_model='deepseek-asr'`；**不新增/修改表与列**，不需要 Alembic。
7. **验收补充**：抽 10 条素材（含 3 条 >120s）与腾讯大模型2.0 做 A/B 对比（字数差异、专名/数字准确率、标点可读性），结果写入交付说明；若明显更差，由作者决定是否保留默认。

## 1. 需求背景

### 1.1 发生了什么变化

2026-11-13，DeepSeek 在原有 API 之外开放了「全家桶应用 API」，其中 **ASR（语音识别）支持独立调用**：`POST https://api.deepseek.com/v1/tools/asr`，一次上传音频返回整段文字。

### 1.2 项目现在的实际情况（不是 `.env` 写的那个）

项目支持 4 家转写服务商，运行时配置存在数据库 `app_kv`，**`app_kv` 优先于 `.env`**：

- `.env` 写的是 `ECHO_ASR_MODE=siliconflow`；
- **`app_kv` 里实际是 `asr_mode=tencent`、`asr_model=16k_zh_en_2.0`**，所以项目当前真正用的是腾讯云录音文件识别（大模型2.0），按 **0.8 元/小时**计费；
- 近三个月实际转写 695 条素材、49.58 小时音频（2026-09 曾用阿里云 2.5 元/小时 + 硅基流动免费，10 月后改腾讯）。

### 1.3 为什么值得接 DeepSeek

| 服务商 | 单价 | 按项目约 14 小时/月 |
|---|---|---|
| 硅基流动 Qwen3-ASR-1.7B | ¥0（免费模型，共享容量，有限流风险） | ¥0 |
| **DeepSeek ASR** | **¥0.78/小时（限时 5 折 ¥0.39）** | **约 ¥10.9（5 折约 ¥5.5）** |
| 腾讯云 录音文件识别 大模型2.0（当前实际在用） | ¥0.80/小时 | 约 ¥11.2 |
| 阿里云 录音文件识别 | ¥2.50/小时 | 约 ¥35 |

- 促销期内比现在省约一半；促销结束（0.78）与腾讯（0.8）基本持平，但项目本来就在用 DeepSeek 的文本模型 + 搜索/抓取，**服务商从 3 家收敛到 2 家**（DeepSeek + 其它后备），少一套密钥和一套计费。
- 代价：DeepSeek ASR 单请求**最长 120 秒、最大 8 MiB**，而项目素材中位数 2.8 分钟、均值 4.28 分钟——**66.3% 的素材超过 120 秒**（这些素材占音频总时长的 **90%**），必须分片。若不分片只截前 120 秒，全库仅能覆盖 **41%** 的语音内容，**59%（29.3 小时）丢失**，视频后半段的结尾金句/结论/CTA 全部缺失，会直接影响对标文案、洗稿、风格资产、复盘和预打标。

### 1.4 分片会不会切在字上

会。按采样点硬切时，切点若落在某个字的发声段中间：前一片该字缺后半、后一片缺前半，ASR 容易丢字或错字，每个切点约影响 1~2 个字；后续「LLM 校对」只能修标点和病句，**救不回没被识别到的音**。

因此本需求的分片规则是「**切在停顿上**」：先用 ffmpeg 逐 50ms 帧分析音量，在每片 90~118 秒的窗口内找**持续 ≥80ms 的静音段**，切在其**中点**（两侧都是静音，不截断任何字）；没有静音段时取窗口内**能量最低的一帧**中心；两者都拿不到（分析失败）才回退到 110 秒硬切并记日志。

实测（本项目 30 条 >2 分钟真实素材）：`-35dB / ≥80ms` 静音判定在 [90,118] 秒窗口内命中 **90%**；其余 10% 走「最安静点」，实测能落在明显停顿上（某 168 秒素材窗口内最安静点 99.45s、RMS -47dB，窗口语音中位数 -24dB）。≤120 秒的素材（占 33.7%）单片直传，**零切点风险**。

### 1.5 成本口径

DeepSeek ASR 按音频时长计费、精确到秒、不足 1 秒按 1 秒计；分片不重叠，总时长不变，**分片本身不增加费用**（只会因每片不足 1 秒的进位产生可忽略的零头）。当前用量约 14 小时/月的口径下：5 折约 5.5 元/月，原价约 11 元/月。

## 2. 想要实现的目标

### 2.1 目标

1. 「AI 设置 → 基础」的 **ASR 服务商**下拉新增「DeepSeek 语音识别」，选中保存后**立即生效**（不需要重启）。
2. 项目**默认切到 DeepSeek**（`.env` + `app_kv` 双改，见 §4.5）。
3. 任意长度的本地素材（最长 2 小时）都能转写：≤118 秒直传；更长的自动按静音切点分片、逐片识别、按顺序拼成完整文案。
4. 失败可读、可重试：鉴权/限流/超时/格式错误给出中文原因；沿用现有「失败通知 + 自动重试退避（3 次）+ 手动重试」。
5. 转写来源可追溯：`transcripts.asr_provider='deepseek'`、`asr_model='deepseek-asr'`，素材编辑页来源显示「DeepSeek」。
6. 不引入新表、不改表结构；不改动其它四家服务商的实现。

### 4.2 转写入口：行为不变，服务商换为 DeepSeek

现有入口全部复用统一 `Transcriber`，选中 DeepSeek 后无需改页面：

### 4.3 长音频自动分片（后台规则，无新按钮）

用户看不到「分片」这个动作，但需要明确规则：

1. 视频/音频先用 ffmpeg 抽/转成 **16k 单声道 16-bit PCM WAV**（DeepSeek 只接受 WAV / Ogg Opus，不接 mp4/mp3）；
2. 探测总时长：
   - ≤118 秒 → **一次请求**发完整音频；
   - >118 秒 → 逐片切分：目标片长 110 秒，窗口 90~118 秒，**切在静音段中点**（静音 = 音量低于 -35dB 且持续 ≥80ms）；窗口内无静音 → 取窗口内能量最低的 50ms 帧中心；仍拿不到 → 110 秒硬切并记 warning；
3. 每片 ≤118 秒、≤8 MiB（16k 单声道 118 秒约 3.8MB，安全）；
4. 单片素材总时长超过 **2 小时** → 明确报错（防异常超长文件把账单跑飞）；
5. 逐片串行调用（不并发），失败片按 `429/503/504` 退避重试 3 次；
6. 所有分片文本按顺序拼接成完整文案，再走现有「LLM 校对 → LLM 预打标 → 落库」。

## 5. 用户故事

1. **作为作者**，我希望在「AI 设置」里选择 DeepSeek 做语音转文字并保存后立刻生效，不需要重启后端、不需要改代码。
2. **作为作者**，我希望不管是 1 分钟的短视频还是十几分钟的长视频，转写出来都是**完整**文案——开头、结尾、金句一个不丢，且不会因为切音频出现莫名其妙的缺字/错字。
3. **作为作者**，当我看到某条素材转写失败时，希望通知里直接告诉我原因（Key 错了 / 限流了 / 视频没声音 / 太长），并且能手动重试，而不是只显示「失败」。
4. **作为项目维护者**，我希望 ASR 服务商只依赖 `.env` 一处密钥、失败时不擅自切到别家（避免悄悄产生别家账单），并且随时可以通过设置页或 `app_kv` 一行配置回滚到腾讯/硅基流动。
5. **作为后续使用者**，我希望在素材编辑页能看出这条转写是 DeepSeek 出的还是腾讯/阿里/硅基流动出的（来源可追溯），方便对比效果和排查问题。

## 9. 风险与前提

1. **促销价不确定**：5 折为「限时」，未标注截止时间；结束后 0.78 元/小时与腾讯 0.8 基本持平——此时接 DeepSeek 的价值主要是「服务商收敛」而非省钱。
2. **ASR 质量未经 A/B**：DeepSeek ASR 与腾讯大模型2.0 的中文口播、专名、数字、标点表现未知，验收时必须双跑对比；若明显更差需作者决定是否保留默认。
3. **分片边界仍有残余风险**：完全无停顿的连读片段会被「最安静点」切，理论上仍可能截到辅音；发生率低、可通过日志发现并人工重转。
4. **限流**：DeepSeek 单账号 50 并发（项目串行调用，远低于上限），但 429 仍可能偶发，需退避重试。
5. **Key 口径**：只认 `.env`；设置页 DB 里的 DeepSeek Key 不会用于 ASR，未配 `.env` 时给出明确引导。
6. **默认切换依赖 DB**：只改 `.env` 不生效（`app_kv` 优先），文档与验收都需覆盖这一点。
