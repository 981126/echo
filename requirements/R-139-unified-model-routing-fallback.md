## 原文（作者原话，未改动）
> 3.除了脚本生成需要双模型参与讨论，其他关于ai的功能默认使用模型1、出现问题在降级成模型2，确保模型1、2都深度学习了该系统数据，不要降级之后模型2像是退化了
> 4.脚本生成里面的讨论轮次是控制了，所有自动生成脚本的讨论轮次

## 澄清与确认结论（2026-09-11）
- **降级触发**：**报错 / 超时 / 空正文 / 输出不合法（JSON 解析失败或不符合该功能契约）** 都降级到模型2。
- **降级可见**：**日志 + 站内通知（功能名/原因/耗时）+ 生成稿标记"由备用模型生成"**。
- **自动生成讨论**：每日自动生成脚本**也走完整双模型讨论**，轮次用设置里的轮次。

## 范围
1. **统一模型路由**（新增 `services/llm_router.py`）：
   - `resolve_slots(db)`：读取模型1/模型2 的（厂家、base_url、model、key）；Key 优先取 DB，回退 `.env`。
   - `generation_pair(db)`：按「生成方 / 评审方」两个下拉解析出两个 slot。
   - `primary_llm(db)`：返回**模型1 + 自动降级模型2** 的客户端；`chat` / `chat_json` 签名与现有 `OpenAIClient` 一致。
   - **参数按厂家归一化**：声明 `supports_temperature`、`min_max_tokens`——避免推理模型"推理吃光 token 导致空正文"这种典型的"降级像退化"。
2. **接入所有非脚本生成的 AI 功能**：人设（init/merge/updates/compare）、视频预打标、转写校对、提示词优化、金样本评测、AI 对话 → 默认模型1，失败降级模型2。
3. **脚本生成**：`debate` 按 `generation_pair` 取生成方/评审方（可相同），轮次取设置；**每日自动生成改走同一套双模型讨论**，并在 `Draft` 上标记使用的模型组合与是否降级。
4. **降级可见**：统一日志；站内通知（功能/原因/耗时）；稿子标记（`Draft.quality` 扩展 `models` / `fallback` 字段）。
5. **"两个模型都深度学习了系统数据"的保障**：
   - 所有功能走**同一套上下文组装与提示词**（两模型输入完全一致）；
   - 参数按厂家归一化（不能因参数不匹配而"看起来退化"）；
   - 输出契约校验 + 同模型重试后再降级；
   - **（建议项，默认做）双模型兼容性自检**：保存模型配置后，用每个功能的极简样例各跑一次模型1/模型2，校验输出契约；不通过则在设置页告警"模型2 在 X 功能上不兼容"。

## 实施补充（2026-09-11 实测发现，已修）
1. **DeepSeek V4.1 Flash 也是推理模型**：`max_tokens` 同时含思考与正文。实测 `max_tokens=3000` 时
   `finish_reason=length`、`reasoning_tokens=3001`、**正文为空**；4000 才有正文。故 `min_max_tokens`
   DeepSeek=4000、Kimi=6000，且「空正文但有思考内容」归类为 `LLMUnusableOutput` →
   **同模型翻倍 max_tokens 重试**，仍失败才降级。
2. **单次调用需要硬性墙钟上限**：httpx 的 read timeout 会被长连接的持续字节重置，实测一次真实评审
   调用挂了 **39 分钟**才失败。`OpenAIClient._post` 改为流式读取 + `ECHO_LLM_TIMEOUT_SECONDS`（默认 600s）
   墙钟上限，超期即按「超时」失败并降级。
3. **流式读取要用 `iter_bytes`**：Kimi 对较长响应返回 gzip（实测 770B gzip / 1401B 解码后 JSON），
   `iter_raw` 只给压缩字节 → JSON 全部解析失败。此坑由「双模型兼容性自检」自动发现并修复。
4. **「无数据到达」的上限要给推理模型留足静默时间**：read timeout 收到 30s 时 Kimi 稳定 40s 被判超时，
   默认配置（生成方=Kimi）每篇都降级，反而制造退化。固定 `READ_TIMEOUT_SECONDS=180s` +
   整体墙钟 deadline 600s 兜底后，自动生成路径实测 `fallback=False`、两方各自正常产出。

## 不包含
- 不引入第三方供应商（厂家目录本次为 DeepSeek / Kimi，加供应商只需在目录加一行）；
- 不做模型微调（"深度学习系统数据"通过统一上下文 + 兼容性自检保证）；
- 不改变 ASR 的白名单校验与降级语义（ASR 无模型2 降级，仍按 R-068/R-094 明确报错）。

## 验收标准
1. 非脚本生成的 AI 功能默认走模型1；制造一次模型1 失败（如临时改错 Key）能自动降级模型2 并产出可用结果。
2. 降级时：日志有记录、站内有通知、生成的稿子带备用模型标记。
3. 脚本生成（手动 + 每日自动）均走生成方/评审方双模型讨论，轮次与设置一致。
4. 空正文 / JSON 解析失败 / 输出不符合该功能契约 三种情况都能触发降级（有测试覆盖）。
5. 参数归一化生效：Kimi（不支持 temperature）与 DeepSeek 走同一调用路径均不报错、不出现空正文。
6. `scripts/verify.sh` 全绿；接口冒烟；前端点检；服务保持运行。
