# R-145 一键「打包 → 上传 → 启动 → 自动增量升级」

- **日期**: 2026-09-12
- **状态**: ✅ 已完成（2026-09-12，M134）
- **关联**: R-144（结构自检/迁移记账/老库升级测试）、`app/main.py`、`app/core/schema_guard.py`、`scripts/release.sh`、`scripts/update.sh`

## 原文（作者原话，未改动）
> 我需要的是，我把这个版本打包上去后，后续我有新版本直接打包部署上去启动就会自动增量新增字段和表

## 澄清：这条链路现在是怎样的
- **新表**：启动时 `Base.metadata.create_all` 自动建 —— 打包部署启动即可，**零额外动作**；
- **新字段**：必须在**那一版代码里**带上 `app/db.py` 的 `_migrate_*` 迁移函数（`create_all` 不给已有表补列），
  启动时幂等执行 —— 也就是说"自动"发生在**部署侧**，而"写迁移"是**发布侧**的一次性开发动作；
  漏写的检测已由 R-144 的老库升级测试 + 启动自检兜住。
- **启动时到底做了哪些变更**：可在启动日志看到「结构自检通过：N 张表；库结构版本=…」。

## 本需求要补的两个缺口
1. **升级前自动备份**：现在「启动即自动升级」，但升级前**不会自动备份** —— 万一迁移有问题，就没有可回滚的库。
   要做法：启动时先判断「模型声明的表/列 vs 实际库」是否一致；**只要有待应用的变更**（含首次引入 `schema_migrations`），
   就在 `init_db()` 之前用 SQLite 官方 backup API 自动备份到 `<data>/backups/pre_upgrade/<时间戳>.db`，
   并做 `integrity_check`；备份失败只告警（站内通知），**不阻断启动**；保留最近 5 份。
2. **打包/部署脚本**：
   - `scripts/release.sh`（本地）：用 `git archive HEAD` 打包（**只含被跟踪文件**，天然排除 `.env`/`data/`/`node_modules/`），
     产出 `dist_release/echo_<版本>_<时间戳>.tar.gz`，并校验包内含后端与 `scripts/`；
   - `scripts/update.sh`（NAS）：升级为「① 升级前备份 → ② 构建 → ③ 启动 → ④ 健康检查 → ⑤ 打印库结构版本」，
     失败即非零退出（不再有静默通过）。

## 不包含
- 不做镜像离线导出（`docker save/load`）——NAS 上 `docker compose build` 已够用，且可避免本地/ NAS 架构不一致；
- 不做自动回滚（回滚仍是「退代码 + 换回备份库」，写进 runbook）；
- 不做迁移的「撤销/降级」语义（本方案只向前升级）。

## 验收标准
1. 用「老结构的库」启动时，会**自动先备份**再升级，备份文件可校验、可用来回滚（有测试）；
2. 全新安装（库文件不存在）**不会**产生无意义的空备份（有测试）；
3. 结构已是最新时，重复启动**不备份、不改动**（幂等，有测试）；
4. `scripts/release.sh` 产出的包**不含** `.env`/`data/`/`node_modules/`，且含 `scripts/backup.sh`（有测试，缺 git 时跳过）；
5. `scripts/update.sh` 含「先备份」「健康检查」「结构版本」三步，且任一步失败即非零退出；
6. `scripts/verify.sh` 全绿；用真实生产库副本演练一次完整「启动即升级 + 自动备份」。
