# R-077-CLOUD-VIDEO-DOWNLOAD: 云端作品视频/音频下载（三平台、低画质可接受）

- **日期**: 2026-09-06
- **提出渠道**: 对话（承接 R-027/D-026 平台真实化与 D-027「视频默认不下载」的演进）
- **原文摘要**: 三个平台（抖音/小红书/B站）的视频+音频都要能拿到；画质可以低一些；先核实第三方（TikHub）是否有此能力。
- **状态**: ✅ 已完成（抖音/小红书可用；B站受 TikHub 线上端点 404 限制暂不可用，代码已预留）
- **排期**: M59（已完成）
- **关联**: PRD §2/§3.2/§3.3、DECISIONS D-026/D-027/D-031、`platform/tikhub.py`、`platform_assets.py`、`media_tools.py`、`media_naming.py`、`works.py /to-local`

## 背景
- 现状（D-027）：平台同步只拉「指标+评论」，**视频默认不下载**；`platform_posts.video_url` 仅抖音列表接口有值（594 条），小红书/B站为空。
- 云端作品「转本地素材」（`POST /api/works/to-local`）目前需要作者**手动上传视频**；作者希望平台上的自己作品视频能**由系统从平台拉流下载**（含音频），免去手动下载再上传，以便本地留存 / 后续转写（R-033 起转本地不自动转写，编辑页手动触发）。
- 上一轮调研建议「先抖音、小红书二期、B站延后」；作者回复：**三个平台视频+音频都是必须的，画质可以低，先确认第三方支不支持**。

## 第三方（TikHub）能力调研结论（2026-09-06，只读核查）
结论：**TikHub 三平台均支持拿流，低画质可行**，但工作量和字段各不相同。

| 平台 | 能力 | 取流方式 | 画质 | 音频 | 下载要求 / 注意 |
|---|---|---|---|---|---|
| 抖音 | ✅ 最简单 | 列表/详情接口已带 `video.play_addr.url_list`（无水印直链，现有 594 条已入库）；可选 `video.bit_rate[]` 中更低档 | 默认即可，可选低档 bit_rate | 含在 MP4 内（单文件） | 服务端下载带 `Referer: https://www.douyin.com/` + 浏览器 UA；直链约 24h 有效，下载前重拉更稳；高画质付费端点（`fetch_video_high_quality_play_url`）**不需要** |
| 小红书 | ✅ 可以 | `GET /api/v1/xiaohongshu/app_v2/get_video_note_detail`（note_id/share_text）返回视频地址（单文件 MP4 无水印，含音轨） | 原画（平台不提供多档选择，1-2 分钟口播体积可控） | 含在 MP4 内 | 仅**视频笔记**有效（图文笔记无视频）；下载必须带 `Referer: https://www.xiaohongshu.com/`（严格防盗链）；小红书近期对 web 端收紧，App V2 为 TikHub 当前唯一推荐稳定系列，实施前需用真实 note 冒烟 1 条确认返回视频地址 |
| B站 | ✅ 可以（最重） | `bilibili/web` 播放流接口（`fetch_video_playurl`，VIP 档走 `fetch_vip_video_playurl`）返回 DASH 流 | **360P/480P 无需登录/Cookie**；720P 需 SESSDATA；1080P+ 需大会员 → 正合「低画质」 | **音视频分离**：video.m4s + audio.m4s 两条流 | 必须 `Referer: https://www.bilibili.com/`（否则 403）；直链约 2h 有效；需下载两条 m4s 后本地 ffmpeg 合并（项目已有 imageio-ffmpeg，`media_tools.py` 可复用） |

补充：TikHub 官方《多平台视频链接下载指南》也确认三平台均为「服务端代下 + 防盗链 Referer + UA」模式，不支持浏览器直连（CORS）。

## 处理方案草案
1. 平台适配层新增「取视频下载地址」：抖音复用列表 play_addr / 重拉详情选低档 bit_rate；小红书调 `get_video_note_detail` 解析视频地址；B站调播放流接口解析 480P（dash.video+audio 最低可用档）。
2. 新增下载服务（参考 `platform_assets._cdn_headers` 的按平台 Referer/UA 头 + httpx 流式落盘；B站额外 m4s 合并 `media_tools`/ffmpeg）。
3. 落盘沿用 R-058「标题-视频」命名（`media_naming`），成功后回填 `videos.filename`/`cover_path`、处理平台 post 绑定；失败/超时/过期重拉降级并留日志。
4. 触发入口与作用范围待作者确认（见下），默认思路：**云端作品「转本地素材」流程内置「从平台下载视频(低清)」选项**，仅在把作品转成本地素材时按需拉流；平台常规同步（D-027）仍不自动下载。

## 反问清单与当前结论
1. **范围与边界**：三平台都支持视频+音频（必须）；低画质即可；平台常规同步仍不自动下载（D-027 保留）。
2. **场景与影响**：把「我」的云端作品转成本地素材时免手动上传；不改变评论/指标同步链路。
3. **数据**：视频直链来自 TikHub 播放流/详情接口（真实性待实施时 1-2 条冒烟确认字段）；拿不到（如小红书图文笔记、B站高画质无 Cookie）则明确报错原因，不静默。
4. **边界与异常**：单条失败不阻塞批量；直链过期→重拉一次→仍失败则跳过并通知；B站合并失败清理临时 m4s；重复下载幂等（已有文件不重复下）。
5. **验收标准**：三平台各挑 1 条真实视频走通「取流→下载→(B站合并)→本地可播放且带音轨」；verify.sh 全绿；mock 模式离线可测。
6. **成本与性能**：下载走平台 CDN（不消耗 TikHub 调用额度之外的解析请求）；B站合并耗时较长，批量用后台任务 + 进度。
7. **依赖与风险**：依赖 TikHub 播放流/详情接口与平台 CDN 防盗链规则；小红书字段/平台风控为最大风险（实施时先冒烟 1 条）。
8. **优先级**：作者已确认三平台必须 → M59。

## 作者确认（2026-09-06）
1. 触发入口 = 素材卡「同步数据」按钮：点同步数据后检查「是否有本地视频文件 + 是否已有文字转译」；都有 → 不下载不转写；没有 → 先下载视频（低清），下载完成自动触发转写。
2. 所有素材卡片都可下载，不区分博主。
3. 转写触发：下载完成即自动转写（复用现有 ASR 流水线）。

## 实施结论（M59，2026-09-06）
1. 三个「同步数据」端点（works/{id}/sync、posts/{id}/sync、videos/{id}/sync）在数据同步后自动预判并投递后台任务 `platform_media`（tasks 新增「素材媒体补齐」通知）；前台提示 + 完成后刷新卡片。
2. 后台补齐逻辑 `services/media_ensure.py`：缺视频按平台优先级（抖音→小红书→B站）解析并下载（`fetch_video_source`），下载成功才建本地素材行；缺转写自动跑 `import_video_task`（ASR→校对→预打标签）。
3. 下载器 `services/media_downloader.py`：带平台防盗链 Referer/UA 流式落盘；B站 DASH 预留 ffmpeg 合并（mp4/dash 均支持）。
4. 真实冒烟（各 1 次请求 + 1 次下载）：
   - 抖音：取到 6 个低清候选直链，实际下载 21MB mp4 成功
   - 小红书：从 `video_info_v2.media.stream.h264` 取到无水印 mp4（含 AAC 音轨），实际下载 15MB 成功
   - B站：`fetch_video_playurl` / `fetch_one_video_v2/v3` / `fetch_video_play_info` 线上均返回 404（当前 TikHub key 未提供该系列端点），代码已按 TikHub SDK 参数接好（bv_id+cid→dash 解析），接口恢复后即可用；当前对纯 B站作品会提示「无可用视频源」而非假下载。
5. 顺带修复：小红书单条详情统计解析（`data.data.data` 为笔记列表，原按 `note.interact_info` 解析导致指标为 0）。
6. 自测：verify.sh 全绿（ruff/mypy/pytest 64+ / 前端 lint+build）；新增 8 个离线测试。
