## 上下文：作者回复对应的 AI 建议（2026-09-10 诊断结论）
作者反馈「AI 提示词功能生成的提示词不准确」，经代码审查 + 真实候选实证，定位三个根因：
1. **所有 key 共用一套语料**：`optimize()` 无论优化哪个 key，都用 `learning_material`（人设 + 风格画像 + 加权转写稿）+ 打分反馈。
   实测优化 `video_tags` / `correct` 产出的候选开头是「你是 R-128 本人的口播标注分身 / 校对分身」——任务被腔调淹没。
2. **无输出契约、无校验**：没把该 key 的必需输出结构（JSON 字段 / 纯文本 / 工具契约）与 user 上下文模板喂给优化器；
   候选生成后不校验能否解析、不与当前版比较、无评分。实证：`generation` v2 候选写「你是 R-128 本人」
   并把作者传记与红线整段**硬写进系统提示词**；而「R-128」并不在当次语料中（人设/红线/风格运行时本就会动态注入）——
   等于重复注入 + 事实不可核 + 档案一改就过期。
3. **没有「准不准」的度量与回流**：`drafts` 未记录所用提示词版本；反馈只取各 3 条 200 字段落，
   未用「AI 原稿 → 作者改写稿」diff、四维分节分、发布后真实互动；自动触发不检查是否已有未处理候选。

## 澄清与确认结论（2026-09-10，作者逐项选择）

4. **评分作用**：只展示「候选 vs 当前版」分数与对比，**启用与否由作者判断**（不设硬门槛）。
5. **评测时机**：**每次产出候选自动跑一遍评分**。
6. **自动触发去重**：**照旧生成**（不因已有未处理候选而跳过）；候选堆积由新增的「拒绝候选」缓解。
7. **附加建议（本次一起做）**：提示词分层模板（风格段不可被优化器改写）、提示词长度预算（超限不采纳）、

## 验收标准
1. 优化任一 key 时，喂入的语料是该 key 的真实相关样本；**确实无样本的 key 返回「样本不足，暂不优化」**，不硬编。
2. 候选产出前经过输出契约校验；未通过按「重试 1 次 → 仍失败则丢弃并返回原因」处理，不入库。
3. 候选正文不含硬写的作者姓名/身份/传记/红线清单（有自动化断言）。
4. 每次候选自动带出「候选 vs 当前版」金样本评分与对比；UI 可查看；启用仍由作者决定。
5. 提示词分层：优化器只改「角色/任务」段，风格段由人设动态生成；候选超长度预算不采纳。
6. 新草稿记录所用提示词版本，反馈可按版本聚合展示（版本效果对比）。
7. 候选可「拒绝」，可一键回滚到任意历史版本。
8. `scripts/verify.sh` 全绿；接口冒烟；服务保持运行。

## 评测稳健性修复（实施中发现，2026-09-10）
- 现象：`correct` 候选评测出现 `empty: 2/3`（AI 回放返回空正文）→ 评分被误判为 47 vs 71。
- 根因：评测最初统一用「生成模型策略」（当时为 kimi 推理模型）跑所有 key；kimi 把 token 预算花在思考上，
  长文本输出（校对稿）在中途被截断 → `content` 为空。
- 修复：
  1. `_eval_llm`：评测模型与该 key **生产时实际使用的模型**保持一致——只有 `generation` 跟随生成模型策略，
     其余功能（video_tags/correct/review/diff/persona_*）生产里都走 DeepSeek，评测也用 DeepSeek；
  2. 回放 `max_tokens` 1200 → 6000；
  3. `_format_ok` 对 JSON 类 key 放宽（允许 ```json 围栏，由 `_parse_json` 兼容）；
  4. 两版回放全为空时标记 `supported=False`（「评测无效」），不再给出误导性低分。
- 复测：`correct` 候选 92.5 vs 当前 92.5（empty 0、errors 0）；`video_tags` 候选 100 vs 当前 60。
