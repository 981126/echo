## 1. 需求背景

R-240/R-241 性能优化及独立复核过程中，顺带发现 4 个**既有缺陷**（非性能优化引入，但影响数据正确性/可靠性），此前只记录未修：

1. **转写稿「一视频多行」**：`videos.transcript` 关系是 `uselist=False`、`docs/DATABASE.md` 也写「video_id 唯一」，但数据库实际只有普通索引 `ix_transcripts_video_id`（非唯一），当前库有 **5 个视频各 2 条转写**。结果：ORM 读到哪一条不确定 → 生成上下文/站内证据/校对可能取错转写稿；未来并发写还可能继续产生重复行。
2. **批量同步单条失败会丢整批**：`platform_sync._ensure_post` 在 `commit=False` 批量模式下，取单条统计失败时执行 `db.rollback()`——会连同**同批其它已写入但未提交**的作品/统计一起回滚（还会丢掉当前这条作品），与注释「单条失败不中断」矛盾；单帖模式下也会把当前作品回滚后返回一个未落库对象。
3. **无主博主时 `GET /api/douyin-review/plans` 500**：handler 直接调用 `video_review_service.current_owner`，无当前主博主时抛 `ValueError` 未捕获 → 500（空库/新部署时会踩到；正常有主博主不触发）。
4. **`_charge_requests` 逐请求事务计费**：`douyin_creator_sync._charge_requests` 对每个请求循环 `_charge(db)`（60 请求=60 事务 + 60 次预算读写），在同步热路径上造成写放大，也可能在循环中途失败留下部分计费。

## 2. 想要实现的目标

### 2.1 核心目标（可验收）

| 项 | 目标 | 验收 |
|---|---|---|
| 转写唯一性 | 一个视频最多一条转写稿；历史重复行按「有正文优先 → asr_status=done 优先 → 最新 id」保留 1 条；并发写安全 | 迁移后 `ix_transcripts_video_id` 为 UNIQUE；重复插入被拒；现有 5 组重复清理为 1 条；相关接口/任务行为不变 |
| 批量同步失败隔离 | 单条统计拉取失败不丢同批其它作品；当前作品仍正常入库（只是缺当天统计）；`BudgetExceeded` 仍向上抛 | 回归测试：批量 2 帖第 2 帖取数异常 → 两帖都入库、第 1 帖有统计、无异常；单帖取数异常 → 作品仍入库 |
| 空博主 500 | 无当前主博主时 `GET /api/douyin-review/plans` 返回 200 + `{"items": []}` | 回归测试（无 creator） |
| 计费事务合并 | 一次 `_charge_requests` 只做 **1 次** `_charge(db, n)`（n=本次真实请求数，超过剩余额度只计剩余并告警） | 回归测试断言单次调用/传入数量；预算语义（不超发、不丢计费）不变 |

### 2.2 明确不做

- 不改 `Video.transcript` 的 ORM 关系形态（仍 `uselist=False`），只把 DB 约束与模型声明对齐已有文档语义（改动面最小）。
- 不改批量同步的其它逻辑/进度/预算取消语义；不重写 `_ensure_post` 的字段更新规则。
- 不改 `plans` 在有主博主时的任何行为；不给其它无主博主接口做批量兜底（只修已发现的这一处异常路径）。
- 不改 TikHub 请求/重试/预算上限语义；`_charge_requests` 仅减少事务次数。
- 不做 R-241 已记录的结构性项（`start_task` worker 池、works 分页等）。

## 4. 功能需求（后端行为，无 UI 变化）

1. 转写稿：
   - 数据迁移清理历史重复（保留规则见 §2.1），并加唯一索引；之后任何写入路径不可能再产生第二行。
   - 读取：`video.transcript` 行为不变（唯一后无歧义）；生成/证据/校对读到的转写稿与最新迁移后保留行一致。
   - 失败/边界：并发创建转写（自动转写 + 手动转写同时触发）时，必须串行化或幂等更新，不允许 500/重复行。
2. 批量同步：
   - 单条作品详情拉取异常：写一条 warning 日志；该作品仍按列表数据入库（标题/描述/封面/发布时间等），统计缺失留给下次同步补；**不影响同批其它作品**。
   - `BudgetExceeded` 仍抛出并触发原有取消逻辑；其它接口/任务返回结构不变。
3. `GET /api/douyin-review/plans`：无主博主 → 200 `{"items": []}`；有主博主 → 与现状完全一致（含 post_id 过滤/limit/排序）。
4. 计费：`_charge_requests` 不改变预算总额与超限告警语义，只把 N 次事务合成 1 次；失败仍只记 warning 不影响主流程。
